## 结论前置

**可行但需精简范围。** 五个星期对于“数据→策略→回测→Docker化→汇报”的完整链条偏紧，建议将项目定位为 **MVP（最小可行产品）**：只做一个经典策略（如双均线或RSI均值回归），用一份Kaggle美股数据跑通全流程，重点是“工程规范 + 可复现演示”，而非追求策略收益。

**分工核心原则：** 1人（核心）负责策略逻辑与回测主引擎；4人每人认领一个相对独立的“外围模块”，降低耦合，便于并行。


## 一、推荐技术栈

| 层级 | 选择 | 理由 |
|---|---|---|
| 数据 | Kaggle Global Markets OHLCV 或 Stock_Market_Datasets | 美股日频数据齐全，CSV格式直接加载 |
| 回测 | 自己写轻量回测循环（不引入backtrader） | 降低学习成本，4周内可控 |
| 策略 | 双均线交叉或RSI均值回归 | 逻辑简单，汇报时容易讲清楚 |
| 环境 | Docker + Docker Compose | 统一Python版本和依赖，避免“在我电脑上能跑” |
| 协作 | GitHub + 简易分支策略 | 核心用main/develop，外围用feature分支 |

**不建议做的事：** 实盘接入、复杂ML模型、期权策略、多因子体系。5周内做不完，且偏离“期末项目演示”的核心目标。


## 二、角色分工

### 角色A（核心负责人）—— 策略与回测主引擎

**职责：** 整条项目链路的“中枢”，代码质量要求最高，由主观能动性强的同学承担。

- 设计项目整体架构（目录结构、模块接口）
- 实现策略逻辑：如短期均线上穿长期均线买入、下穿卖出
- 编写回测引擎：持仓计算、交易记录、收益曲线
- 计算核心指标：累计收益、最大回撤、夏普比率（简化版即可）
- 协调各模块接口对接

**为什么需要“接口设计先行”：** 外围同学需要知道“你的数据长什么样、你的策略需要什么输入、你的回测输出什么格式”。核心同学应在第1周产出接口定义文档。

### 角色B —— 数据层

**职责：** 让所有人能“一键获取干净的数据”。

- 从Kaggle下载选定数据集，筛选出5-10只美股标的（建议AAPL、MSFT、GOOGL、AMZN、TSLA等）
- 数据清洗：处理缺失值、统一日期格式、确保按时间排序
- 封装成简单API：`load_data(tickers, start, end) -> DataFrame`
- 用Docker卷挂载方式提供数据，避免每人重复下载

**难度评价：** 低。pandas基础操作即可完成。

### 角色C —— 回测可视化与报告输出

**职责：** 把角色A的计算结果变成“能看懂、能展示”的图表。

- 绘制价格曲线 + 买卖信号标记点
- 绘制策略收益曲线 vs 买入持有收益曲线
- 绘制回撤曲线
- 整理回测指标为表格/JSON格式，供汇报PPT使用

**技术选型：** Matplotlib即可。不追求交互式图表。

**难度评价：** 低。重点是把角色A的输出格式对齐。

### 角色D —— Docker与运行环境

**职责：** 确保“任何人拿到仓库都能跑起来”。

- 编写 `Dockerfile` 和 `docker-compose.yml`
- 固定Python版本（如3.10），锁定依赖版本
- 提供 `run.sh` 或 Makefile：`docker compose up` 即完成全流程
- 处理Kaggle数据的挂载或下载说明

**为什么这是独立角色：** Docker调试经常踩坑（路径、权限、网络），交给一人专注处理，避免全组卡住。

**难度评价：** 中等偏低。有现成模板可参考。

### 角色E —— GitHub协作规范 + 文档 + 汇报材料

**职责：** 项目的“面子工程”和协作秩序。

- 第1周建立仓库、分支保护规则、PR模板
- 维护 `README.md`：项目简介、运行方式、分工说明
- 整理最终汇报PPT：问题背景→方法→结果→局限
- 确保每次PR有人审查、有commit message规范

**为什么需要专人负责：** 期末项目中协作规范和文档经常被忽视，最后导致代码混乱、汇报时没人讲得清“谁做了什么”。

**难度评价：** 低，但琐碎。


## 三、五周时间安排

### 第1周：定方向 + 搭骨架

| 角色 | 任务 | 交付物 |
|---|---|---|
| A | 确定策略逻辑、设计模块接口 | 接口定义文档（数据格式、函数签名） |
| B | 下载Kaggle数据、筛选标的、初步清洗 | `data/` 目录 + 数据说明 |
| C | 调研可视化库、等待A的结果格式 | 确认图表清单 |
| D | 搭建Dockerfile骨架、验证基础环境 | 能跑通 `python --version` |
| E | 建GitHub仓库、分支策略、README初稿 | 仓库可访问、分支规则生效 |

**周检查点：** 全组能坐在一起，A讲解“我们的项目架构长什么样”。

### 第2周：核心逻辑 + 数据通道

| 角色 | 任务 | 交付物 |
|---|---|---|
| A | 实现策略逻辑 + 回测循环初版 | 能对单只股票跑出信号 |
| B | 完成数据加载API，对接A的接口 | `load_data()` 可用 |
| C | 实现1张图：价格+信号标记 | 初版图表 |
| D | Docker挂载数据卷、跑通B的数据加载 | `docker compose run` 能读数据 |
| E | 跟踪PR进度、更新README | 协作记录 |

**周检查点：** 集成测试——A + B 的代码能否合在一起跑。

### 第3周：集成 + 指标 + 可视化

| 角色 | 任务 | 交付物 |
|---|---|---|
| A | 完善回测：加入手续费、滑点简化处理；计算夏普、回撤 | 完整回测结果 |
| B | 支持多标的批量加载 | 数据层稳定 |
| C | 完成3张核心图表 + 指标表格 | 可视化完整 |
| D | Dockerfile完整版；写 `run.sh` 一键流程 | `docker compose up` 可跑 |
| E | 整理中期进展、准备PPT框架 | 中期汇报材料 |

**周检查点：** 全流程在Docker内跑通一次。

### 第4周：调优 + 文档 + 彩排

| 角色 | 任务 | 交付物 |
|---|---|---|
| A | 策略参数微调、结果复现 | 最终回测报告 |
| B | 数据说明文档、Kaggle来源标注 | 数据文档 |
| C | 图表美化、导出为汇报用格式 | PPT-ready图表 |
| D | 修复Docker运行中的环境问题 | 稳定镜像 |
| E | 完成PPT初稿、README终版 | 汇报材料v1 |

**周检查点：** 全流程彩排一次，计时。

### 第5周：汇报准备

| 角色 | 任务 |
|---|---|
| A | 主讲策略与结果 |
| B | 辅助讲数据来源与处理 |
| C | 演示图表与指标 |
| D | 现场演示 `docker compose up` （或录屏备用） |
| E | 控制时间、补充细节 |

**最后两天：** 全组统一PPT口径，确保“数据→策略→回测→可视化→Docker化”的逻辑线清晰。


## 四、关键风险与应对

| 风险 | 应对 |
|---|---|
| Docker环境卡住超2天 | 角色D跳过完美方案，先用本地虚拟环境备份 |
| 策略回测结果太差 | 期末项目重点是“流程走通”，不是“赚钱”；汇报时主动讨论局限 |
| 角色B的数据格式和A不匹配 | 第1周接口文档必须写清楚列名和索引类型 |
| 有人进度落后 | 角色A/E在第2、3周检查点主动介入，拆分任务 |
